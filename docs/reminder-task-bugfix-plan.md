# Reminder and Task Bug Fix Plan

## Goal

Restore reminder/task creation, listing, grouping, and completion by aligning the Flutter task flow with the Supabase schema and the existing GoRouter/Riverpod architecture.

## Investigation Summary

The reminder/task screens are wired through GoRouter and Riverpod correctly:

- `RouteConstants.reminder`, `newReminder`, `today`, `scheduled`, and `completed` are registered in `lib/core/constants/routers/app_router.dart`.
- `NewReminderScreen` creates a `TaskEntity` and calls `createTaskProvider`.
- `ReminderScreenContent`, `TodayScreen`, `ScheduledScreen`, and `CompletedScreen` all read `tasksProvider`.
- `markTaskDoneProvider` invalidates `tasksProvider` after updates.

The likely break is in the data/schema contract, not routing.

## Root Causes

### 1. No `tasks` table migration exists

No checked-in Supabase migration defines `public.tasks`. The app assumes a table with:

- `id`
- `task_name`
- `description`
- `user_id`
- `isDone`
- `deadline`
- `created_at`

Without a migration, local and deployed environments can drift, and new setup cannot reproduce the feature.

### 2. User ID type mismatch

Profiles are UUID-based:

```sql
id uuid primary key references auth.users(id) on delete cascade
```

But task code currently uses `SupabaseUserContext.currentUserId()`, which returns `int`, and `TaskReadDto.userId` is also `int`.

That conflicts with the current profile/auth model. If `tasks.user_id` is UUID, parsing fails. If `tasks.user_id` is integer, it no longer matches the profile schema and RLS pattern.

### 3. Column naming is inconsistent

`TaskDto.toJson()` writes `tasks_name`, but `TaskRemoteDatasource.createTask()` manually inserts `task_name`.

Read code expects `task_name`. This does not currently break because `toJson()` is not used, but it is a maintenance trap.

### 4. Date toggle does not affect saved reminders

`NewReminderScreen` has `_isDateEnabled`, but `_handleSave()` always uses `_selectedDate`. Turning date off still saves the selected/current date.

### 5. No RLS policy plan for tasks

Task queries filter by `user_id`, but the migration should enforce ownership with RLS:

- users can select their own tasks
- users can insert tasks for themselves
- users can update their own tasks
- users can delete their own tasks if delete support is later added

## Recommended Design

Use Supabase auth UUIDs as the single owner identifier for tasks.

The `tasks.user_id` column should be `uuid references public.profiles(id) on delete cascade`, and Flutter should use `Supabase.instance.client.auth.currentUser!.id` for task ownership. This matches the existing profile table and Supabase RLS pattern.

Keep task queries inside `data/data_source/task/task_remote_datasource.dart`. Keep providers as UI state only.

## Implementation Plan

### Task 1: Add the tasks migration

Create a migration under `supabase/migrations/`:

```sql
create table if not exists public.tasks (
  id bigint generated by default as identity primary key,
  task_name text not null,
  description text not null default '',
  user_id uuid not null references public.profiles(id) on delete cascade,
  is_done boolean not null default false,
  deadline timestamptz not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index if not exists tasks_user_deadline_idx
  on public.tasks(user_id, deadline);

create index if not exists tasks_user_is_done_deadline_idx
  on public.tasks(user_id, is_done, deadline);

alter table public.tasks enable row level security;

drop policy if exists "Users can read their own tasks" on public.tasks;
drop policy if exists "Users can insert their own tasks" on public.tasks;
drop policy if exists "Users can update their own tasks" on public.tasks;

create policy "Users can read their own tasks"
  on public.tasks
  for select
  to authenticated
  using ((select auth.uid()) = user_id);

create policy "Users can insert their own tasks"
  on public.tasks
  for insert
  to authenticated
  with check ((select auth.uid()) = user_id);

create policy "Users can update their own tasks"
  on public.tasks
  for update
  to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);
```

Use snake_case `is_done`, not `isDone`, to match Postgres conventions.

### Task 2: Add UUID user context support

Modify `lib/data/data_source/supabase_user_context.dart`:

- keep `currentUserId()` only if other integer-ID tables still need it
- add `currentAuthUserId()` returning `String`
- throw `Exception('User is not authenticated')` when there is no current user

Expected method:

```dart
String currentAuthUserId() {
  final user = Supabase.instance.client.auth.currentUser;
  if (user == null) {
    throw Exception('User is not authenticated');
  }
  return user.id;
}
```

### Task 3: Update task DTO/entity ownership type

Modify:

- `lib/data/models/task/task_read_dto.dart`
- `lib/domain/entities/api/task/task_api_entity.dart`

Change `userId` from `int` to `String`.

Read `is_done` from Supabase, with temporary compatibility for `isDone`:

```dart
isDone: (json['is_done'] ?? json['isDone']) as bool,
```

Read `user_id` as `String`:

```dart
userId: json['user_id'] as String,
```

### Task 4: Update task datasource column mapping

Modify `lib/data/data_source/task/task_remote_datasource.dart`.

Use `currentAuthUserId()` and `is_done`:

```dart
final userId = userContext.currentAuthUserId();

await _supabase.from('tasks').insert({
  'task_name': dto.tasksName,
  'description': dto.description,
  'user_id': userId,
  'is_done': false,
  'deadline': dto.deadline,
});
```

Select:

```dart
'id, task_name, description, user_id, is_done, deadline, created_at'
```

Update:

```dart
await _supabase
    .from('tasks')
    .update({'is_done': true})
    .eq('id', id)
    .eq('user_id', userId);
```

### Task 5: Fix `TaskDto.toJson()`

Modify `lib/data/models/task/task_dto.dart` so it uses `task_name`, not `tasks_name`.

### Task 6: Fix date toggle behavior

Modify `lib/presentation/screens/screen_contents/contents/new_reminder_screen.dart`.

Decide the product behavior:

- Recommended: Date cannot be disabled for a persisted task because grouping requires a deadline.
- Alternative: If date is disabled, save today with selected time and label it as a general reminder.

Recommended implementation:

- remove the date toggle, or keep it visually disabled
- always require a date
- keep time optional

### Task 7: Add focused tests where practical

Add unit tests for:

- `TaskReadDto.fromJson()` parses UUID `user_id`
- `TaskReadDto.fromJson()` accepts `is_done`
- task filtering logic for today/scheduled/completed, preferably extracted into a small helper

### Task 8: Verify

Run:

```bash
dart format lib/data/data_source/supabase_user_context.dart lib/data/data_source/task/task_remote_datasource.dart lib/data/models/task/task_dto.dart lib/data/models/task/task_read_dto.dart lib/domain/entities/api/task/task_api_entity.dart lib/presentation/screens/screen_contents/contents/new_reminder_screen.dart
dart analyze
```

Manual verification:

- create a new reminder
- confirm it appears in Reminders
- create a reminder due today and confirm it appears in Today
- create a future reminder and confirm it appears in Scheduled
- mark a today/reminder item complete
- confirm it moves to Completed and disappears from active lists

## Notes

Do not rename the whole `domain/entities/api` folder during this fix. That is naming debt from the old API migration and should be handled separately to avoid hiding the task/reminder bug under a broad refactor.
